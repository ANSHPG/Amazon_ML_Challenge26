## 1. Methodology Used

### 1.1 Problem Statement
The challenge requires linking business records from a deduplicated reference source (Source 1) to matching records in two independent, noisy data sources (Source 2 and Source 3). Each Source 1 entity may match zero, one, or many records from Source 2 and Source 3. The evaluation metric is the macro averaged F_0.5 score, which heavily penalizes false positives (incorrectly merging distinct businesses) more than false negatives (missing a valid link).

### 1.2 High Level Approach
Our solution is a multi stage deterministic and heuristic pipeline consisting of four sequential phases:

1. **Data Preprocessing**: Normalize, clean, and compact all text fields across all three data sources.
2. **Blocking and Candidate Generation**: Build inverted indexes on S2 and S3 using composite blocking keys to drastically reduce the comparison search space.
3. **Feature Engineering and Pairwise Scoring**: Compute exact match, token level Jaccard similarity, and fuzzy string similarity features for each candidate pair.
4. **Threshold Based Classification**: Apply optimized multi tier matching rules to classify each candidate pair as a match or non match.

### 1.3 Data Scale
* Source 1 (Training): ~1 million records (deduplicated reference)
* Source 2 (Training): ~5 million records
* Source 3 (Training): ~5 million records
* Source 1 (Test): 1,732,544 records
* Source 2 (Test): millions of records
* Source 3 (Test): millions of records

The core columns used across the pipeline are: `entity_id`, `business_name`, `business_address`, and `country`.

## 2. Data Preprocessing

### 2.1 Text Normalization (`normalize_text`)
All business name and address fields across S1, S2, and S3 undergo the following normalization:

1. **Null Handling**: Any missing or NaN value is replaced with an empty string.
2. **Case Folding**: All text is converted to lowercase.
3. **Ampersand Expansion**: The `&` character is replaced with the word ` and ` (e.g., "AT&T" becomes "at and t").
4. **Punctuation Removal**: All non alphanumeric characters are stripped using the regex pattern `[^a-z0-9\s]` and replaced with spaces.
5. **Whitespace Normalization**: Multiple consecutive spaces are collapsed into a single space, and leading/trailing whitespace is stripped.

### 2.2 Legal Suffix Removal (`normalize_name`)
For business names specifically, common corporate legal suffixes are removed after normalization. The following 13 terms are stripped:

`incorporated`, `inc`, `corporation`, `corp`, `limited`, `ltd`, `llc`, `llp`, `private`, `pvt`, `company`, `co`, `limitedliabilitycompany`

For example, "ABC Retail Private Limited" is normalized to "abc retail".

Address normalization (`normalize_address`) does not strip these legal suffixes because address fields may contain valid tokens like "company road" or "limited lane".

### 2.3 Compaction (`compact`)
After normalization and cleaning, all whitespace is completely removed from the string using the regex `\s+` replaced with an empty string. This produces a continuous alphanumeric fingerprint of the text. For example:

* "abc retail" becomes "abcretail"
* "wal mart" and "walmart" both become "walmart"

This step bridges spacing variations that would otherwise prevent exact string matching.

### 2.4 Token Signature (`token_signature`)
A permutation invariant representation is generated by extracting unique tokens, sorting them alphabetically, and joining with spaces. This allows matching when tokens appear in different orders across sources (e.g., "retail abc" and "abc retail" produce the same signature).

## 3. Candidate Generation and Blocking Strategy

### 3.1 The Scaling Problem
A naive comparison of every S1 record against every S2 and S3 record would require approximately:

* 1 million S1 records multiplied by 10 million S2+S3 records = **10 trillion pairwise comparisons**

This is computationally infeasible. Our blocking strategy reduces the average number of comparisons to approximately **23.4 candidates per S1 query**, bringing the total to roughly **40.5 million comparisons** across the entire test set.

### 3.2 Blocking Key Construction
For every record in S2 and S3, we construct three composite blocking keys by concatenating the country with different combinations of the compacted business name and address, separated by a pipe delimiter:

* **Country Name Key**: `{country}|{compact_name}`
  Example: `india|abcretail`
* **Country Address Key**: `{country}|{compact_address}`
  Example: `india|12mgroadnewdelhi`
* **Country Name Address Key**: `{country}|{compact_name}|{compact_address}`
  Example: `india|abcretail|12mgroadnewdelhi`

Country partitioning is critical because it ensures that businesses from different countries are never compared against each other, which improves both precision and runtime.

### 3.3 Inverted Index Construction (`build_index`)
For each of the three blocking keys, we build an inverted hash map (Python `defaultdict(list)`) where:

* **Key**: The composite blocking key string
* **Value**: A list of `entity_id`s from S2 and S3 that share that key

This is built by iterating through every row of S2 and S3 using `itertuples(index=False)` for performance.

### 3.4 Candidate Retrieval (`candidates_for_row`)
For each S1 query entity, we generate its three blocking keys and look them up in the corresponding inverted indexes. The final candidate set is the **union** of all retrieved entity IDs across the three indexes:

```
Candidates(s1_row) = Index_name(key1) ∪ Index_addr(key2) ∪ Index_name_addr(key3)
```

Using three complementary keys ensures high recall: even if a business name is slightly different, the address key may still retrieve the correct match, and vice versa.

## 4. Model Architecture and Feature Engineering

### 4.1 Pairwise Feature Computation (`pair_features`)
For every candidate pair (one S1 record and one S2/S3 candidate), we compute six similarity features:

| Feature | Description | Range |
| :--- | :--- | :--- |
| `name_exact` | Binary flag: 1 if the compacted names are identical, 0 otherwise | {0, 1} |
| `addr_exact` | Binary flag: 1 if the compacted addresses are identical, 0 otherwise | {0, 1} |
| `name_token` | Token level Jaccard similarity between the normalized business names | [0.0, 1.0] |
| `addr_token` | Token level Jaccard similarity between the normalized business addresses | [0.0, 1.0] |
| `name_fuzzy` | RapidFuzz `token_set_ratio` between the normalized business names, scaled to [0, 1] | [0.0, 1.0] |
| `addr_fuzzy` | RapidFuzz `token_set_ratio` between the normalized business addresses, scaled to [0, 1] | [0.0, 1.0] |

### 4.2 Token Level Jaccard Similarity (`jaccard_tokens`)
The Jaccard similarity between two strings is computed by splitting them into whitespace delimited token sets:

```
Jaccard(A, B) = |A ∩ B| / |A ∪ B|
```

where A = set of tokens from string a, and B = set of tokens from string b. Returns 0.0 if either set is empty.

### 4.3 Fuzzy String Similarity (RapidFuzz `token_set_ratio`)
The `fuzz.token_set_ratio` from the RapidFuzz library tokenizes both strings, identifies their intersection and remainder substrings, and computes a Levenshtein distance based ratio. This method is immune to token reordering and duplicate words, making it ideal for matching business names with varying word orders or repeated tokens. The raw score (0 to 100) is scaled to [0.0, 1.0].

If RapidFuzz is not installed, the pipeline gracefully falls back to using the exact match indicator as the fuzzy score.

### 4.4 Weighted Heuristic Match Score (`match_score`)
A composite score is computed as a weighted sum of all features:

```
Score = 4.0 * name_exact + 4.0 * addr_exact + 2.0 * name_fuzzy + 2.0 * addr_fuzzy + 1.0 * name_token + 1.0 * addr_token
```

The maximum possible score is 14.0. Exact matches receive the highest weight (4.0), fuzzy similarity receives moderate weight (2.0), and token overlap receives the lowest weight (1.0). This weighting reflects the confidence hierarchy: an exact string match is far more reliable than a partial token overlap.

## 5. Matching Rules and Classification (`is_match`)

The final match decision uses a cascaded, disjunctive rule system. A candidate is classified as a match if **any** of the following conditions are satisfied:

### Validation Pipeline Thresholds (used during threshold optimization):
* **Rule 1**: `name_exact = 1` AND `addr_exact = 1` (both fields match exactly)
* **Rule 2**: `name_exact = 1` AND `addr_fuzzy >= 0.90` (exact name with high address similarity)
* **Rule 3**: `addr_exact = 1` AND `name_fuzzy >= 0.92` (exact address with high name similarity)
* **Rule 4**: `name_fuzzy >= 0.96` AND `addr_fuzzy >= 0.88` (both fields have very high fuzzy similarity)

### Inference Pipeline Thresholds (optimized values used for final predictions):
* **Rule 1**: `name_exact = 1` AND `addr_exact = 1`
* **Rule 2**: `name_exact = 1` AND `addr_fuzzy >= 0.84`
* **Rule 3**: `addr_exact = 1` AND `name_fuzzy >= 0.92`
* **Rule 4**: `name_fuzzy >= 0.92` AND `addr_fuzzy >= 0.84`

The rules are intentionally conservative and precision oriented to align with the F_0.5 metric, which penalizes false merges twice as heavily as missed links.

## 6. Validation and Threshold Optimization

### 6.1 Validation Strategy
Rather than randomly subsampling from S2 and S3 (which would destroy ground truth match pairs and make evaluation meaningless), we use a targeted semi synthetic validation sampling technique:

1. Sample 50,000 S1 records from the training set.
2. Identify all true positive target entity IDs from the ground truth labels for those S1 records.
3. Filter the full S2 and S3 datasets to retain only the true positive matching records.
4. Add 50,000 random distractor (negative) records from S2 and S3 to test the model's false positive resistance.
5. Apply the full preprocessing and blocking pipeline only to this focused validation subset.

This approach preserves the ground truth relationships while introducing realistic noise, enabling accurate F_0.5 evaluation without processing the entire 10 million record corpus during validation.

### 6.2 Threshold Grid Search
We perform a systematic grid search over two parameters:

* **Name Threshold (nt)**: Tested values [0.92, 0.94, 0.96]
* **Address Threshold (at)**: Tested values [0.84, 0.88, 0.92]

For each combination, we use a factory function `make_rule(name_threshold, addr_threshold)` that returns a customized matching classifier. The grid search evaluates each threshold pair using the macro averaged F_0.5 metric against the ground truth validation set.

### 6.3 Evaluation Metric: F_0.5 Score
The F_beta score with beta = 0.5 is defined as:

```
F_0.5 = (1.25 * Precision * Recall) / (0.25 * Precision + Recall)
```

Where:
* Precision = |True Positives| / |Predicted Positives|
* Recall = |True Positives| / |Actual Positives|

**Edge cases handled:**
* If both the true set and predicted set are empty (correct singleton prediction): F_0.5 = 1.0
* If the predicted set is empty but the true set is not (missed matches): F_0.5 = 0.0
* If both precision and recall are zero: F_0.5 = 0.0

The final macro F_0.5 is computed as the arithmetic mean of the per entity F_0.5 scores across all validation S1 entities.

### 6.4 Validation Results
Our optimized thresholds achieved a validation macro F_0.5 score of approximately **0.67** on the 50,000 entity validation subset.

## 7. Inference and Scaling

### 7.1 The Memory Challenge
The test dataset contains 1,732,544 Source 1 entities. Running the full feature computation and matching loop on all entities in a single pass would exhaust available memory on standard compute instances.

### 7.2 Chunking Architecture
To solve this, we implemented a chunking strategy:

* **Chunk Size**: 100,000 rows per chunk
* **Number of Chunks**: 18 (covering all 1,732,544 test rows)
* **What is chunked**: Only the Source 1 test dataset is split into chunks. Source 2 and Source 3 are loaded entirely into memory and their inverted indexes are built once and reused across all chunks.
* **Chunk Selection**: For each chunk `i`, the pipeline processes rows from index `i * 100,000` to `min((i+1) * 100,000, total_rows)`.

### 7.3 Per Chunk Processing
For each chunk, the pipeline:

1. Slices the appropriate 100,000 row segment of test S1.
2. Generates candidate pairs for each S1 row by querying the pre built S2 and S3 inverted indexes.
3. Computes pairwise features for all candidates.
4. Applies the optimized matching rules to classify each pair.
5. Saves two intermediate files:
   * `matching_results_chunk_{i}.tsv`
   * `candidate_pairs_chunk_{i}.tsv`

### 7.4 Chunk Stitching
After all 18 chunks are processed, a final stitching cell concatenates all chunk files:

1. Reads all `matching_results_chunk_{0..17}.tsv` files.
2. Concatenates them into a single `matching_results.tsv`.
3. Reads all `candidate_pairs_chunk_{0..17}.tsv` files.
4. Concatenates them into a single `candidate_pairs.tsv`.

The chunking and stitching process does not alter any predictions. Each chunk is independently processed against the same complete S2/S3 index, so the final stitched output is mathematically identical to what a single pass run would produce.

### 7.5 Output Validation
Before saving, the pipeline runs a comprehensive validation suite (`validate_outputs`) that checks:

* 100% coverage: every S1 entity in the test set has exactly one row in the output.
* No duplicate `source1_entity_id` rows.
* No duplicate matched IDs within any single row's ID list.
* All predicted IDs exist in the S2 or S3 test datasets.
* All matches are strict subsets of the corresponding candidate pairs (a matched ID that was never a candidate would indicate a pipeline bug).

### 8.1 Output Statistics
Our final inference run on the complete 1,732,544 test entities produced:

| Metric | Value |
| :--- | :--- |
| Total S1 Entities | 1,732,544 |
| Total Singletons (No Match Found) | 444,097 (25.6%) |
| Total Linked Pairs | 2,580,875 |
| Total Candidates Evaluated | 40,583,712 |
| Average Candidates per S1 Query | 23.4 |

### 8.2 Search Space Reduction
The blocking strategy achieved a massive reduction in the comparison space:

* **Without blocking**: 1,732,544 * (millions of S2 + millions of S3) = trillions of comparisons
* **With blocking**: 40,583,712 total comparisons (average 23.4 per query)

This represents a reduction factor of several orders of magnitude while maintaining high recall through the use of three complementary blocking keys.

### 8.3 Singleton Distribution
Approximately 25.6% of S1 entities were classified as singletons (no matching record found in S2 or S3). This is consistent with real world entity resolution scenarios where not every reference entity has a corresponding record in the target databases. Correctly predicting singletons contributes a perfect F_0.5 = 1.0 for each such entity, directly boosting the macro average.

### 8.4 Evaluation on Real Dataset / Leaderboard Score
When evaluated against the official ground truth on the real test dataset, our solution achieved a **final macro F_0.5 similarity score of approximately 0.746**.
This confirmed that our composite blocking inverted indexes, paired with fine-grained fuzzy and token-level similarity filtering tuned specifically for high precision, generalised exceptionally well from the training subset to the full test distribution (including unseen regions such as France).

## 10. Key Design Decisions

### 10.1 Why Deterministic Rules Instead of a Trained ML Model?
The F_0.5 metric heavily penalizes false positives. A deterministic, threshold based approach gives us full control over the precision/recall tradeoff. By setting conservative thresholds validated against ground truth, we ensure high precision while accepting slightly lower recall. This is optimal for the F_0.5 evaluation criterion.

### 10.2 Why Three Blocking Keys Instead of One?
A single blocking key (e.g., country + name) would miss valid matches where the business name differs but the address is identical. By using three complementary keys, we ensure that a match can be retrieved through any combination of name and address similarity, maximizing the recall ceiling of our candidate generation stage.

### 10.3 Why Chunking?
Processing 1.7 million entities in a single pass would require holding all intermediate candidate pairs and feature vectors in memory simultaneously. Chunking to 100,000 rows per pass keeps the memory footprint manageable on standard compute instances while producing mathematically identical results.

### 10.4 Country Partitioning
All blocking keys are prefixed with the country field. This is both a correctness and performance decision: businesses in different countries should never be matched, and partitioning by country reduces the inverted index lookup size proportionally. This approach also naturally handles the unseen test country (France) without any code changes.

## 11. Memory and Throughput Optimizations

### 11.1 PyArrow CSV Engine
For loading the large test datasets (S2 and S3 are each several hundred MB), we use `pd.read_csv()` with `engine="pyarrow"` and `dtype_backend="pyarrow"`. This provides multithreaded SIMD based CSV parsing with significantly reduced memory footprint compared to the default C engine.

### 11.2 In Memory Dictionary Caching
After building blocking indexes, the full S2 and S3 DataFrames are converted into dictionary lookups via `.set_index("entity_id").to_dict("index")`. This enables O(1) random access to any candidate record by its entity ID during the matching loop, avoiding expensive DataFrame row indexing operations.

### 11.3 Explicit Memory Lifecycle Management
After the inverted indexes and dictionary caches are constructed, the original S2 and S3 DataFrames are explicitly deleted with `del` followed by `gc.collect()`. This frees hundreds of megabytes of RAM that would otherwise remain allocated, ensuring sufficient headroom for the inference loop.

### 11.4 Fast Row Iteration
All row level loops use `df.itertuples(index=False)` instead of `df.iterrows()`. The `itertuples` method returns lightweight namedtuples rather than full Pandas Series objects, providing a 10x to 50x speedup in tight loops with millions of iterations.

### 11.5 Column Projection
All TSV reads are restricted to `CORE_COLS = ["entity_id", "business_name", "business_address", "country"]` using the `usecols` parameter. This prevents loading any auxiliary columns that may exist in the raw data, reducing both I/O time and memory consumption.

### 11.6 Graceful Dependency Fallbacks
Both `polars` and `rapidfuzz` are imported inside `try...except` blocks with boolean flags (`HAS_POLARS`, `HAS_RAPIDFUZZ`). If either library is unavailable, the pipeline automatically falls back to pure Pandas operations and exact match indicators respectively, ensuring the pipeline runs on any Python environment without installation failures.
